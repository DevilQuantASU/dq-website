# Contributing to DevilQuant

Thank you for helping improve the DevilQuant website. This guide describes the normal path from choosing a feature to merging and deploying it.

## 1. Choose a Feature

Start with an issue, roadmap item, bug report, or a small improvement that fits the website. Before writing code:

1. Check open issues and existing pull requests so the work is not duplicated.
2. For a new feature, describe the user problem, expected behavior, and affected page or component.
3. Keep the first change focused. Split unrelated cleanup into a separate change.
4. Ask for clarification in the issue or pull request when the desired behavior is unclear.

## 2. Set Up Locally

Clone the repository, enter the project directory, install dependencies, and create a branch from the latest `main`:

```bash
git clone https://github.com/DevilQuantASU/dq-website.git
cd dq-website
npm install
git switch main
git pull --ff-only origin main
```

Do not work directly on `main` or `gh-pages`.

## 3. Name Your Branch

Use a category and a short kebab-case description:

```text
feature/add-project-roadmap
fix/mobile-navbar-overflow
docs/add-contributing-guide
chore/update-dependencies
```

Use these categories when possible:

- `feature/` for new functionality
- `fix/` for bug fixes
- `docs/` for documentation
- `chore/` for maintenance and tooling
- `refactor/` for behavior-preserving code changes

Create the branch from `main`:

```bash
git switch -c feature/short-description
```

## 4. Develop and Verify

Start the development server while working:

```bash
npm run dev
```

Before opening a pull request, run the checks locally (CI runs the same ones on every PR):

```bash
npm run lint
npm run check-links
npm run build
```

Use the Node version in `.nvmrc` (Node 22; Vite 7 needs at least 20.19).

`npm run build` creates the production files in `dist/`. It also creates `dist/404.html`, which redirects plain paths like `/about` to their hash URLs (`/#/about`) on GitHub Pages. The fallback-file step is implemented in `scripts/create-spa-fallbacks.mjs` so it works on Windows, macOS, and Linux without shell-specific commands.

## 5. Name Commits

Use short, imperative commit messages with a type prefix:

```text
feat: add project roadmap page
fix: correct mobile navbar spacing
docs: explain deployment workflow
chore: update Vite
refactor: simplify leader card props
```

Keep commits focused and avoid mixing unrelated changes. Commit the source and configuration files, but do not commit `dist/` or `node_modules/`.

```bash
git add src/ CONTRIBUTING.md package.json scripts/
git commit -m "feat: add project roadmap page"
git push -u origin feature/short-description
```

## 6. Open and Merge a Pull Request

Open a pull request from your branch into `main`.

The pull request description should include:

- What changed and why
- How the change was tested
- Screenshots or a short recording for visual changes
- Any follow-up work or known limitations

After review, address requested changes with additional focused commits. Once the pull request is approved and checks pass, merge it into `main`. Delete the feature branch after merging when it is no longer needed.

## 7. Build and Deploy

A build on a feature branch only verifies that branch locally. It does not publish anything:

```bash
npm run build
```

Deployment is automatic. The `CI` workflow (`.github/workflows/ci.yml`) runs on every pull request: lint, internal link check, and build. A PR should not be merged until it passes. When a PR is merged into `main`, the same workflow re-runs the checks and then publishes `dist/` to the generated `gh-pages` branch. GitHub Pages detects that push and runs its `pages-build-deployment` workflow.

A weekly `External links` workflow (`.github/workflows/links.yml`) checks external URLs. It can also be run manually from the Actions tab.

Manual deploy is still available as a fallback, from an up-to-date `main`:

```bash
git switch main
git pull --ff-only origin main
npm run deploy
```

Do not edit or commit directly to `gh-pages`; it is generated by the deployment. After a merge, verify that the `CI` deploy job and the Pages workflow both completed successfully.

## Windows, macOS, and Linux

The build uses Node.js for filesystem operations rather than PowerShell `copy` or Unix `cp` commands:

```json
"build": "vite build && node scripts/create-spa-fallbacks.mjs"
```

This command is intentionally the same on every operating system. To change which fallback files are created, edit `scripts/create-spa-fallbacks.mjs`; do not replace the command with OS-specific shell syntax.

Git commands work in PowerShell, Command Prompt, macOS Terminal, and Linux shells. If a local shell needs a different command for navigation or environment variables, keep that difference in local setup instructions rather than changing the shared npm scripts.

## Deployment Checklist

- The PR's `CI` checks passed and it is merged into `main`.
- The `CI` deploy job on `main` completed successfully.
- The GitHub Pages workflow completed successfully.
- The live site was checked at https://devilquant.com.
